## 二、掌握度模型

### 2.1 7 个状态与旧模型的关系

原 `learning_profiles` 只有 PRD 6.1 的 5 个状态（`not_started` / `learning` / `pending_verification` / `mastered` / `review_due`），被计划排期、每日任务、测验范围、前端「学习档案」等 30 多个既有链路读取。**本阶段不改它的取值集合、CHECK 约束和语义**，而是新增一张「掌握度状态」表，两者通过 Service 层的统一写入口保持同源。

| 新状态 | 中文 | 含义 | 投影到 `learning_profiles` |
| --- | --- | --- | --- |
| `NOT_STARTED` | 未开始 | 无任何记录 | `not_started` |
| `LEARNING` | 学习中 | 每日任务已开始 | `learning` |
| `SELF_REPORTED_COMPLETED` | 用户自述完成 | 用户说自己学完了，**无验证证据** | `pending_verification` |
| `UNDERSTOOD` | 基础理解通过 | 基础理解 / 代码阅读类题目全部答对 | `pending_verification` |
| `APPLIED` | 应用练习通过 | 应用练习判定通过，或应用类题全对 | `pending_verification` |
| `MASTERED` | 真正掌握 | 知识点测验（≥3 题全对且 ≥90 分）或诊断测验（≥2 题全对）通过 | `mastered` |
| `NEEDS_REVIEW` | 需要复习 | 正式验证未通过，或练习失败 | `review_due` |

- 反向映射 `LEGACY_TO_MASTERY` 用于历史数据补建：`pending_verification → self_reported_completed`、`review_due → needs_review`。
- Alembic 升级时执行 `_backfill_mastery_from_profiles()`，把既有档案一次性补建为掌握记录，**老用户不会因升级而掌握度清零**；重复升级不覆盖已有记录。
- 双向投影在 `MasteryService._write()` 与 `_sync_legacy()` 中一并发生：改当前态 + 写一条证据 + 同步旧状态，不允许只做其中一步。

### 2.2 状态机（纯函数，可单测）

`app/services/mastery_rules.py` 只回答三个问题，规则不散落在 Service 里：

| 事件 | 规则 | 关键约束 |
| --- | --- | --- |
| 开始学习 `on_start` | 仅 `not_started → learning` | 已有状态不降级 |
| **用户自述** `on_self_report` | 仅 `not_started` / `learning → self_reported_completed` | **代码路径上不存在「自述 → MASTERED」的分支**；已 MASTERED 的自述不降级 |
| 练习通过 `on_exercise` | `→ applied` | 已 MASTERED 不因多练一次降级 |
| 练习失败 | `→ needs_review` | 已 MASTERED 时保持掌握（单次练习失败不足以推翻完整验证），只记证据并给复习建议 |
| 测验 `on_quiz` | `mastered` / `applied` / `understood` 向上推进且不回退 | **`NEEDS_REVIEW` 是唯一能把 MASTERED 拉下来的路径**——正式验证未通过 |
| 跳级 `is_skip_allowed` | 仅 `mastered` 返回 `True` | 自述、基础理解、应用练习都不够 |

测验等级判定 `derive_quiz_level()` 严格从高到低、不跨档跳：
`MASTERED`（题量≥阈值、全对、≥90 分）→ `APPLIED`（应用类题全对）→ `UNDERSTOOD`（基础类题全对）→ `NEEDS_REVIEW`（基础类题有错）。题目分类为空的历史题库按「基础理解」对待。

### 2.3 掌握证据（需求三的 8 个字段全部落库）

| 需求字段 | 落点 |
| --- | --- |
| 用户标识 | `knowledge_mastery.user_id` / `mastery_evidence.user_id`（单用户模型，仍保留多用户扩展空间） |
| 知识点 ID | `knowledge_point_id`，两表均有索引；`(user_id, knowledge_point_id)` 唯一约束 |
| 练习记录 | `exercise_attempts`（答案、判定、覆盖率、评分依据、判定时间）+ `mastery_evidence.exercise_attempt_id` |
| 测验记录 | `mastery_evidence.quiz_attempt_id` 外键指向 `quiz_attempts`；`knowledge_mastery.quiz_attempt_id` 记最近一次 |
| 正确率 | `accuracy`（0—100，当前态与每条证据各存一份） |
| 测验难度 | `quiz_difficulty`（`beginner` / `intermediate` / `advanced`，取该次测验最高难度） |
| 掌握状态 | `knowledge_mastery.status` + 证据的 `status_before` / `status_after` |
| 验证时间 | `verified_at`；另有 `self_reported_at`（自述时间）与 `review_due_at`（进入复习时间），三者**分开存，不互相覆盖** |

证据来源 4 类：`self_report` / `exercise` / `quiz` / `placement`。`mastery_evidence` **只追加、不覆盖**，因此学习记录与测验历史可长期回溯。

**练习判定不执行用户代码**：`grade_exercise_answer()` 用「参考答案二元组覆盖率」做确定性文本比对，阈值 `EXERCISE_PASS_COVERAGE = 0.6`（能容忍换变量名/换顺序，拦得住答非所问）；参考答案缺失时抛 `ValueError` 转 422，不会默默判「通过」。

### 2.4 数据库变更（迁移 `d8cfe871faa5`）

只做增量，不改既有表结构：

| 变更 | 说明 |
| --- | --- |
| 新增 `knowledge_mastery` | 当前态，每用户每知识点唯一；含 7 态 CHECK 约束 |
| 新增 `mastery_evidence` | 证据流水，含 `source` / `status_after` 两个 CHECK 约束 |
| 新增 `exercise_attempts` | 练习记录，含 `result` CHECK 约束 |
| `learning_plan_versions` 加 `self_reported_kp_codes` | 自述快照，**不参与跳过**，与 `mastered_kp_codes`（只装有证据且实际被跳过的知识点）分离 |
| `quiz_attempts` 加 `purpose` | `practice` / `placement`。用独立列而非改 `scope_type` 的 CHECK——SQLite 改 CHECK 要重建表，且该表被 `mistakes` / `review_tasks` 外键引用，风险高于收益 |

`quiz_attempts.purpose` 同时暴露到 `QuizAttemptOut` 与 `QuizAttemptSummaryOut`，测验历史列表可区分「诊断测验」与「普通练习」。

## 三、诊断流程

### 3.1 六维画像（需求四）

`DIMENSIONS` 固定 6 个维度，每维映射到**具体锚点知识点**（不是整门课的平均分）：

| 维度 | 课程 | 锚点知识点数 | 示例锚点 |
| --- | --- | --- | --- |
| Python 基础 | `python-basics` | 7 | 变量、字符串、列表、字典、函数、条件判断、for 循环 |
| Python 工程能力 | `python-advanced` | 5 | 类与对象、继承、装饰器、类型注解、venv |
| 数据库能力 | `python-database` | 5 | 主键、SELECT、JOIN、事务、关系映射 |
| Web 后端能力 | `fastapi-backend` | 4 | HTTP 方法、REST、响应体、Depends |
| 大模型 API 能力 | `llm-api` | 4 | OpenAI 兼容、消息角色、对话状态、Token 预算 |
| LangGraph Agent 能力 | `langgraph-agent` | 6 | Agent 三要素、State 结构、路由函数、工具节点、检查点、stream_mode |

锚点用 `(稳定 code, 名称关键字)` 二元组定义，课程目录调整导致 code 变动时按名称兜底解析；课程不存在时维度标记 `available=false` 并给出说明，不编造数据。

每个知识点输出 `status` / `status_label` / `source`（`evidence` 有验证证据 / `claim` 仅自述 / `none` 无记录）/ `accuracy` / `verified_at`。**自述单独标 `claim`，不计入覆盖率，也不会被算成已掌握**。维度等级分 `mastered` / `partial` / `not_started` / `no_data`。

### 3.2 诊断 → 个性化学习路线

```
POST /api/v1/diagnosis {learning_goal, target_course_code}
   │
   ├─ 1. 补建历史数据：bootstrap_from_legacy()（老档案 → 掌握记录）
   ├─ 2. 逐维盘点：按锚点知识点读 knowledge_mastery，统计 5 类计数与覆盖率
   ├─ 3. 确定路线范围：目标课程 + 递归展开的全部先修课程（按课程 order 排序）
   ├─ 4. 逐知识点判定动作：
   │      mastered            → skip     跳过（已有掌握证据）
   │      self_reported / understood / applied → verify  验证（诊断测验）
   │      needs_review        → review   复习
   │      未满足的先修知识点  → remedial 补学先修
   │      其余                → study    学习
   │  同一知识点有多种诉求时按 remedial > review > verify > study > skip 取最紧急
   ├─ 5. 汇总 skippable / needs_verification / remedial 三张清单 + 摘要 + notes
   └─ 6. 输出 DiagnosisOut（维度画像 + 有序 route 步骤 + 汇总结论）
```

开发库副本实测「学习 LangGraph」目标：`route` 152 步，前两步为补学先修 `python-basics-05-02` / `python-basics-06-03`，第三步起进入 Python 基础正常学习；6 个维度均为 `not_started`（库内无掌握记录时）；`notes` 明确写出「只采信掌握证据」。

### 3.3 跳级与补学（需求五）

| 要求 | 实现 |
| --- | --- |
| 1. 已掌握可跳过 | 学习计划排期与学习路径默认读取 `MasteryService.mastered_kp_codes()`（只有 `mastered`），不再采信请求参数 |
| 2. 先修补学建议 | 诊断路线输出 `remedial` 动作与 `remedial_kp_codes`；`skip-check` 输出 `blocked` 清单 |
| 3. 诊断测验验证 | `POST /api/v1/diagnosis/placement`，**唯一允许对未学知识点出题**的入口；`purpose=placement`，通过后写 `placement` 证据并进入 `MASTERED` |
| 4. 不允许仅凭自述跳过全部前置 | 计划的 `mastered_kp_codes` 改为只记「有证据且被实际跳过」的知识点；请求里自述的 code 落到 `self_reported_kp_codes` 快照并写自述证据，但**不进排期跳过集合**。学习路径接口默认按证据计算，`preview=true` 才用请求参数做假设推演 |
| 5. 薄弱知识点复习 | `GET /api/v1/mastery/review-suggestions` 给出原因、建议动作、可练练习 code 与可测题量；路线里 `needs_review` 生成 `review` 步骤 |
| 6. 学习记录与测验历史保留 | 证据流水只追加；`quiz_attempts` 原样保留并新增 `purpose`；`exercise_attempts` 独立存练习记录；两者都不删历史 |

### 3.4 端到端链路（开发库副本实测）

```
A 自述 python-basics-02-01 → self_reported_completed，next_action=「做一次知识点测验验证：自述不等于掌握」
B 诊断「学习 LangGraph」  → 该知识点 source=claim，维度覆盖率 0%，出现在 needs_verification_kp_codes，skippable=[]
C 诊断测验（2 题全对）    → mastery_updates[0] = {status: mastered, reasons: 「诊断测验抽样验证：2 道题全部通过，百分制 100 分」}
D 跳级检查               → skippable=['python-basics-02-01']，needs_verification=[]
E 证据流水               → [('placement','mastered'), ('self_report','self_reported_completed')] 只追加
F 旧档案投影             → learning_profiles.status = mastered（计划与每日任务照常跳过）
```

## 六、开发期间发现并修正的真实缺陷

1. **目录种子难度非法值**：阶段 4D 目录里 4 个课时难度写成 `basic`，`seed_course_catalog` 抛 `ValueError`，34 个既有测试连带全红 → 改为合法值 `beginner`。
2. **`Store` 注入写法**（阶段 5 之前的遗留，已在 4D 处理）：本阶段沿用新模型不改旧接口。

4. **`diagnosis_service` 时间字段**：误用了不存在的 `utc_today_naive` 作 `started_at` → 改 `utc_now_naive()`；`_action_for` 签名多余参数、`_build_route` 缩进错误逐一修正。
5. **路线补学缺位**：先修检查只查 `kp.prerequisites` 且顺序被后置知识点覆盖 → 按课程分组先建立 `position` 索引，先修项一定排在被依赖知识点之前。
6. **诊断摘要文案**：`no_data` 维度未归入「待开始」导致摘要漏项 → 汇总时合并 `not_started` 与 `no_data`。
7. **既有测试期望与新规则冲突**：
   - `test_plan_api.py` 三个用例靠「请求参数里写已掌握」来跳过 → 改为先用 `MasteryService.grant_mastery()` 写入真实掌握证据；

## 八、边界与未完成内容

- **不执行用户提交的代码**：练习判定是确定性的文本覆盖率比对，不 `eval`、不起子进程；阈值 `0.6` 是产品策略值，未做语义等价判断（如改写变量名可过、意思对但用词完全不同可能不过）。
- **诊断测验是抽样验证**：每个知识点 2 题全对即判 `MASTERED`，属于「跳级抽样」而非完整认证；正式知识点测验仍要求 ≥3 题、全对、≥90 分。
- **诊断锚点是人工选定的关键知识点**，不是整门课所有小节；维度覆盖率反映锚点掌握比例，不等于课程完成度。
- **课程 `publish_status` 仍为 `draft`**、教材内容仍为 `reviewed`，人工终审后置 `published`（与阶段 4D 一致）。
- **无真实用户历史数据**：开发库 `learning_profiles` 为空，迁移的补建逻辑经单测覆盖 `bootstrap_from_legacy()`，但未在含大量历史档案的生产库上跑过。
- 前端「能力诊断」页只做展示与发起（自述、预检、生成诊断测验），答题仍在「测验中心」完成；没有新增图表库或第三方依赖。
