### 2.4 对话消息数据结构

`messages` 表在批次 1 通过一次 Alembic 迁移扩展（PRD §11 建议字段）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `message_type` | String(32)，NOT NULL | `text` | 消息类型，取值见 3.3 |
| `structured_data` | JSON 文本，可空 | NULL | 卡片结构化数据，仅卡片消息写入 |
| `card_version` | String(16)，可空 | NULL | 卡片协议版本；`text` 消息为 NULL |

`status` 的 CHECK 由 `('completed','error')` 扩为 `('completed','error','streaming','stopped')`；`role` 的 CHECK 保持。存量消息回填 `message_type='text'`、`structured_data=NULL`、`card_version=NULL`、`status` 不变。

`MessageOut` 同步增加三字段；`ConversationService._is_context_message()` 保持「仅 `status=completed` 进模型上下文」的语义，新增状态与卡片消息不得把半成品喂给模型。

### 2.5 卡片消息数据结构

10 类消息类型（PRD §6 / 任务书阶段 5）：`text`、`task_card`、`lesson_card`、`quiz_card`、`quiz_result_card`、`mistake_card`、`plan_card`、`plan_change_card`、`progress_card`、`error_card`。其中 8 类为交互卡片（任务书阶段 8），`text` 为普通文本，`error_card` 为失败态与未知版本降级态。

- `structured_data` 必须是**完整 JSON 对象**，含 `card_version`、`type` 与类型专属载荷；前后端共用一份字段表，`lib/cards.ts` 用 TypeScript 判别联合类型表达，校验写成纯函数并配单测。
- 卡片数据只来自后端业务结果（Service 返回值）；前端不得从聊天文字推断卡片内容，也不得推断知识点掌握状态（PRD §3.3 第 5 条）。
- 未知 `message_type` 或不受支持的 `card_version` → 降级为 `error_card`，明确展示失败，不渲染空白。
- 刷新恢复：`GET /conversations/{id}` 返回消息三字段，卡片按类型重放；不另存「卡片渲染结果」。

### 2.6 前后端 API 通信方案

**沿用**：同源 `/api/v1` 代理、`lib/api.ts` 请求封装与 401 处理、SSE 通过 `fetch` + `ReadableStream` + `TextDecoder` 解析、`X-Accel-Buffering: no`、Bearer 会话令牌、Agent 双层超时（120 秒整体 + 模型超时）。

**新增 3 个接口**（均在 `conversations` 路由）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `PATCH` | `/conversations/{id}` | 会话重命名（局部更新，只接受 `title`） |
| `POST` | `/conversations/{id}/messages/stop` | 停止生成：进程内运行注册表终止流，落 `status=stopped` 的部分消息并发 `done` |
| `POST` | `/conversations/{id}/messages/regenerate` | 重新生成，仅对普通文本回复开放，不重复写入用户消息 |

**右侧四面板复用既有只读接口，不新增聚合端点**：

| 面板 | 接口 |
| --- | --- |
| A 当前学习计划 | `GET /plans/current`、`GET /plans/{id}/versions/{n}` |
| B 今日学习任务 | `GET /daily-tasks/today?generate=false` → 无任务才 `POST /daily-tasks/today/generate`（先查后生成，保证幂等） |
| C 当前知识点 | `GET /knowledge-points/{code}`、`GET /lessons/{lesson_code}`、教材内容接口 |

## 3. 契约冻结（批次 1–5 不得擅自变更）

### 3.1 消息状态机

`streaming`（助手开始生成）→ `completed`（正常完成）/ `error`（模型或工具失败，保留部分文本与原因）/ `stopped`（用户停止，保留部分文本）。用户消息恒为 `completed`。只有 `completed` 进入模型上下文；任何状态都不得把未完成回复伪装为完整回复（PRD §3.2 输入框要求）。

### 3.2 SSE 事件契约

| 事件 | data 字段 | 变更 |
| --- | --- | --- |
| `start` | conversation_id, user_message_id, model, title, intent, sub_intent | 沿用 |
| `delta` | text | 沿用 |
| **`card`** | conversation_id, message_id, card_version, message_type, structured_data | **新增**：一次性下发完整 JSON，禁止 `card_delta` 增量拼接 |
| `done` | conversation_id, message_id, model, title, message_count, intent, sub_intent, subgraph, result_status | 沿用；`stopped` 时同样发出 |
| `error` | conversation_id, message_id, message | 沿用 |

`card` 帧仅在 JSON 完整且 `card_version` 受支持时渲染；未完成帧丢弃并降级 `error_card`（PRD §11 明文要求）。

### 3.3 卡片类型与版本

`card_version` 采用 `v1` 起算的字符串；类型表与载荷字段在 `lib/cards.ts` 与后端 `app/schemas/cards.py` 双向对齐，字段名不转换。批次 1 冻结，后续扩展只增版本、不改 `v1` 语义，旧聊天记录按版本降级展示。

**契约细化（批次 1 落地，不改变 `v1` 语义）**：

- SSE `card` 帧的 `structured_data` 是**一张完整卡片对象** `{"card_version","type","payload"}`；未知版本/类型/不完整 JSON 由 `normalize_card()` 纯函数降级为 `error_card`，绝不渲染半成品。
- 持久化到 `messages.structured_data` 的是**完整卡片集合对象** `{"card_version","type","cards":[...]}`，`cards` 中每个元素都是完整卡片对象。这样一条助手消息可携带多张卡片，仍不新增消息行、不改变 `message_count` 口径（§3.4）；`message_type` 取首张卡片类型，普通文本为 `text`。
- 失败回复（`status=error`）按 §3.5 写 `message_type=error_card` 与一张 `error_card`；`stopped` 保留纯文本，不写卡片。
- 生成开始时预建 `status=streaming` 的助手消息并计数 +1，完成/失败/停止只更新同一行；因此 `start` 与 `card` 帧都能携带真实 `message_id`。只有 `completed` 进入模型上下文。
- `POST /conversations/{id}/messages/regenerate` 返回 JSON `MessageOut`（非 SSE），复用原始用户消息、上下文截止到该用户消息，新增一条助手回复；不接受卡片消息重新生成。`POST /messages/stop` 为幂等置位接口，真正落 `stopped` 由 SSE 生成器在事件边界完成。

### 3.4 计数与一致性口径

- 卡片**附属于同一条助手消息**，不新增 `messages` 行；`learning_sessions.message_count` 仍由用户消息与助手消息两处各 +1，卡片不额外计数。
- 删除会话只删会话、消息与学习会话，不删学习计划、测验、错题等独立业务数据（PRD §12 数据验收）。
- 右面板只显示后端返回值；掌握状态以 `knowledge_mastery` 7 态为准，不从聊天文字推断。

### 3.5 失败与降级

模型未配置 → 409 且不保存用户消息、不创建空会话；模型超时 / 工具失败 → `error` 事件 + `status=error` 落库 + `error_card`；回复已生成但落库失败 → 明确报错不伪装成功；客户端断连 → 保留已生成部分并标记中断。

## 4. 数据库迁移设计（批次 1 实现）

- 单份迁移，`down_revision = "7e6ec48dafbe"`，保持线性链。
- SQLite 的 `messages` 带两条 CHECK 约束，必须用 `batch_alter_table`（表重建迁移）；沿用阶段 6 的 `7e6ec48dafbe` 惯例，迁移内显式 `PRAGMA foreign_keys` 与外键保留。
- 迁移前用 `python -m app.cli backup-db` 备份；执行 `upgrade → downgrade → re-upgrade` 演练；校验 `alembic check` 零漂移、`PRAGMA integrity_check = ok`、`foreign_key_check` 无输出、存量消息行数与内容不变。
- 项目曾出现「版本号已 head 但列缺失」的迁移漂移（阶段 6 记录），批次 1 必须以 `PRAGMA table_info(messages)` 实测列存在，不以 `alembic current` 代替。
- 回滚：代码回滚必须连库回退，旧代码版本链不认识新 `revision`（迁移版本号）会导致启动脚本失败；用 `restore-db` 恢复升级前备份，并导出 `.secret_key`（模型密钥加密文件）。

### 9.8 收尾：真实浏览器布局量测与一处真实缺陷修复

量测方式：静态快照 `xiaoma-v14-layout.html` 直接引用 `frontend/app/globals.css`，用 Edge headless + CDP `Emulation.setDeviceMetricsOverride` 强制精确视口（Edge 的 `--window-size` 有最小宽度限制，直接量测 375 会得到 492，不能作为 375 的证据），读取 `getBoundingClientRect()` 与 `documentElement.scrollWidth`。

**发现并修复的真实缺陷**：375px 下 `.window-main` 宽度为 `0px`，移动端中栏整体不可见。根因是 `@media (max-width: 1279px)` / `(max-width: 767px)` 把 `.window-rail` 与 `.window-right` 改为 `position: fixed`，两者脱离 CSS Grid 流；`.window-columns` 仍声明 3 条轨道（窄屏为 `0px minmax(0,1fr) 0px`），唯一在流内的 `.window-main` 被自动放置进第 1 条 `0px` 轨道。修复方式是给三栏显式指定列位：

```css
.window-rail { grid-column: 1; ... }
.window-main { grid-column: 2; }
.window-right { grid-column: 3; ... }
```

**排除一次量测假阳性**：初版快照把结果 JSON 追加进 `<pre>`（`white-space: pre`），把 `scrollWidth` 撑到 871，误报「375px 横向溢出」。移除该测量元素后 `scrollWidth` 回到 375；抽屉虽在视口外（`right=708`），但为 `position: fixed` + `visibility: hidden`，不产生可滚动溢出。已给 `<pre>` 加 `pre-wrap` / `overflow-wrap`，并在量测表达式中先移除测量元素再取值，避免用假阳性冒充缺陷或用假阴性冒充通过。

## 11. 批次 5 落地：Agent 产卡、卡片按钮与消息级操作（2026-11-09）

### 11.1 范围与一条产品裁决

### 11.2 Agent 产出卡片的映射表

唯一入口是 `backend/app/agent/cards.py::cards_for_state()`，由主图 `finalize` 节点调用。**在父图节点发射**而不是在 planning / quiz / review 子图内部发射：嵌套子图的 custom 事件不会自动冒泡到父图流（teaching 子图早前用显式 `emit` 参数绕过同一问题），在 `finalize` 能一次性读到各子图回传的 `tool_results`。

| `planning` / `plan_overview` | `plan_card` | `CurrentPlanOut`，生效版本优先、其次待确认草案 | 无任何版本 |

每张卡片出口都过 `validate_card_payload()` 自检，字段缺失就**不发卡**，宁缺不降级：不发半成品，前端就不会因为后端缺字段而展示 `error_card`。

| 操作 | 前端 | 后端 | 边界 |

### 12.3 三处真实缺陷与修复（均由本批真实 GUI / 打包暴露）

**缺陷一：preload 在 sandbox 下整体失效（严重）**

现象：窗口能显示界面，但状态页的「重试 / 选择目录」按钮点了没反应；新增的标题栏环境标记也没生效。

### 12.5 打包环境坑与可复现命令

本机打包踩到三个坑，均已在代码或文档中处理，换机器打包时可直接照做：

1. **`ELECTRON_RUN_AS_NODE=1`**：终端若带这个变量（Electron 系应用常设置），`electron.exe` 会退化成纯 Node，`--version` 输出 Node 版本、不创建窗口也不开 CDP。启动窗口前必须从环境里剔除该变量。
2. **electron-builder 内置下载器返回 502**：同一 URL 用 `curl` 正常（HTTP 200），内置下载器被代理拦。解决方式是先用 `curl` 把三个资源下到本地并校验 sha256，再用本地静态服务 + `ELECTRON_BUILDER_BINARIES_DOWNLOAD_OVERRIDE_URL` 提供。
3. **override URL 的 host 不能带端口**：electron-builder 会把 host 当作缓存子目录名，`127.0.0.1:8899` 含冒号，Windows 下 `mkdir` 直接 `ENOENT`。必须用 80 端口，让 host 为 `127.0.0.1`。

资源版本与校验值（取自 `app-builder-lib/out/toolsets/windows.js`）：

| 文件 | sha256 |
|---|---|
| `winCodeSign-2.6.0.7z` | `cdaec7154dda7cc31f88d886e2489379a0625a737d610b5ae7f62a12f16743a4` |
| `nsis-3.0.4.1.7z` | `9877df902530f96357d13a7a31ae2b9df67f48b11ffc9a1700a7c961574ec5fa` |
| `nsis-resources-3.4.1.7z` | `593a9a92ef958321293ac6a2ee61e64bf1bd543142a5bd6b3d310709cc924103` |

可复现命令（PowerShell）：

```powershell
# 1) 准备本地资源源（80 端口，host 不能带端口）
node $env:TEMP\xm-b6-bins\serve.js

# 2) 打包
cd D:\XiaoMa\desktop
$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"
$env:ELECTRON_BUILDER_BINARIES_DOWNLOAD_OVERRIDE_URL = "http://127.0.0.1"
$env:ELECTRON_BUILDER_BINARIES_ALLOW_HTTP = "true"
npm run dist:win
```

网络正常的机器不需要第 1、2 步的环境变量，直接 `npm run dist:win` 即可。

| 错题复习 | 我有哪些错题？帮我复习一下 | review/analyze_mistakes | 同上 | `mistake_card` | 0.1 s | 同上 |

- **真实模型确认**：`start` 帧 `model=deepseek-chat`，讲解正文 839 字由模型流式产出，不是模板拼接；范围内复测（「print() 具体怎么用」）得 996 字，`lesson_card.payload.explanation` 与 SSE 文本逐字一致。
- **答案隔离复核**：`quiz_card.payload` 的键只有 `attempt_id/questions/scope_name/total_points`，题干对象只有 `id/stem/question_type/options`；全串检索 `correct_answer`/`explanation`/`is_correct`/`score` 均为 `false`，PRD §5.4 的隔离在真实数据上成立。
- **业务门槛也是真的**：对未学习知识点组卷时，后端返回「该知识点尚未学习，不能进行正式测验」，Agent 如实转述、不产卡——这轮一开始就是因为这个门槛没拿到 `quiz_card`，换成已学习知识点（`python-basics-01-01`）后才产出。

### 13.2 三处必须知晓的边界（不是「全绿」）

1. **超范围提问仍会产 `lesson_card`**：会话绑定「第一个程序：print 输出」时问「列表是什么」，模型按系统提示先声明「列表不在本次知识点范围内」再引导，而 `build_lesson_card()` 只要 `context.knowledge_point` 存在且回复非空就发卡，于是这张卡片的 `explanation` 实为**范围说明**而非讲解正文。属语义边界，需产品裁决：是否对「范围说明类回复」不发讲解卡片。本批不改，避免用中文关键词启发式去猜回复性质。*（已由批次 8 §14.2 解决：改用结构化标记 `[[out_of_scope]]`，超范围回复不再发讲解卡。）*
2. **`quiz_result_card` 在聊天链路没有生产者**：`cards_for_state()` 只经 `quiz` 工具结果产卡，而 `generate_quiz` 返回的一定是 `started` 状态；全库检索 `submit_quiz_result` / `submit_exercise` 在 `app/agent/subgraphs/` 下**零调用**，即提交永远走 REST。因此 9 类卡片里 8 类可由真实链路产出，`quiz_result_card` 当前无生产路径（单测覆盖的是纯函数分支，不等于可达）。*（已由批次 8 §14.3 解决：新增只读意图 `quiz/quiz_result`，9 类卡片全部可达。）*
3. **卡片与消息的关系仍是一条**：7 个用例里每轮只有 1 条助手消息，卡片写进该消息的 `structured_data`，未新增消息行 —— 与 §11.1 的裁决一致。

### 14.2 超范围讲解卡：结构化标记而非关键词猜测

批次 7 明确拒绝「用中文关键词猜回复性质」。本批改用提示词协议：

- `_TEACHING_RULES` 新增第 8 条：问题与当前知识点无关、需要先说明范围时，模型在正文**最前面**单独输出一行 `[[out_of_scope]]`，随后另起一行写正文；属于当前知识点时不得输出该标记。
- `app/agent/scope_marker.py` 的 `ScopeMarkerFilter`：在转发增量前缓冲判定，标记跨增量分片（`[[out_of_` + `scope]]`）也能剥掉；判定不是标记时原样补发，不丢字、不改写正文；`flush()` 处理「模型只输出了一个前缀就结束」。
- `teaching` 子图把剥离后的正文作为 `reply`，并回传 `reply_scope`；`finalize` 传入 `cards_for_state(reply_scope=...)`，`out_of_scope` 时**不下发**讲解卡。
- 失败模式是 **fail-open**：模型不输出标记时行为与批次 5 完全一致（照发讲解卡），不会出现「该发卡却没发」的新故障。

真实模型（`deepseek-chat`）四例实测：

| 用例 | 会话知识点 | 命中意图 | 结果 |
|---|---|---|---|
| 「列表是什么？」 | 什么是编程与 Python | teaching/teach | 无卡片、`message_type=text`、流与库中均无标记 |
| 「print() 具体怎么用？」 | 同上 | teaching/teach | 同上（模型判定为后续知识点） |
| 「我想了解什么是编程，帮我讲讲这个知识点」 | 同上 | teaching/teach | `lesson_card`，`explanation` 与 SSE 文本、库中正文逐字一致 |
| 「Python 是一门什么样的语言？」 | 同上 | teaching/teach | 同上 |

即：同一知识点下，范围内产卡、范围外不产卡，且标记从未出现在流式内容与聊天记录里。

### 14.3 成绩卡片：只读路径，不碰「提交只走 REST」

- 意图：`quiz` 分支新增 `quiz_result`；触发词为「成绩 / 得分 / 分数 / 测验结果 / 考了多少 / 得了多少分 / 对了几道 / 错了几道 / 上次测验」。这几个词本身已指向一次测验的结果，不必再出现「测验」二字；**「分数」例外**——它在数学语境另有含义，必须与测验词同时出现，避免把「讲讲分数和小数的区别」路由到测验子图（该用例已固化为测试）。
- 工具：`AgentToolbox.get_latest_quiz_result()` → `QuizService.list_attempts()`（按 `started_at` 倒序，已过滤 `review` 范围）+ `get_attempt()`，取第一条 `submitted` 的完整结果。只读，不写库。
- 文案：`_compose_result()` 输出范围、得分、答对/答错题数、提交时间、掌握度变化与下一步引导，数字全部取自 Service。
- 卡片：`cards_for_state` 的 `quiz_result` 分支只经 `build_quiz_result_card`，未提交或未评分的尝试**不产卡**；已提交结果才带 `correct_answer` / `explanation` / `score`，与 PRD §5.4「未提交不下发答案」不冲突。
- 实测：真实链路「我上次测验得了多少分？」→ `quiz/quiz_result`，产出 `quiz_result_card`（0 / 30 分、答对 0 题答错 3 题，逐题含正确答案与解析）；「查看我的测验记录」仍是 `quiz_history`，只出文字列表、不出卡。

### 15.4 卸载与残留

**卸载又踩了同一个坑，且结论要改**：在 Git Bash 里执行 `"Uninstall Xiaoma.exe" //S`，退出码 0，但等 30 秒后安装目录 19 项 **一个都没删**、注册表项仍在、无卸载进程残留——典型的「假成功」（批次 7 记录 `//S` 可用，这次不成立，说明 Git Bash 的参数改写不稳定）。改用 `Start-Process` 调用卸载器并 `-Wait` 之后退出码 0，安装目录被整体删除。**结论：卸载一律用窗口终端工具（PowerShell）发起，不要用 Git Bash。**

卸载后核查：

| 项 | 结果 |
|---|---|
| 安装目录 `%LOCALAPPDATA%\Programs\Xiaoma` | 已删除 |
| 注册表卸载项 / `App Paths` | 均已清除 |
| 桌面快捷方式 / 开始菜单项 | 均已清除 |
| `%APPDATA%\xiaoma-desktop` | 保留（22 项，窗口状态与缓存） |
| 运行中的容器与数据卷 | 保留（`xiaoma-*` 容器继续跑 `project-*` 镜像，卷 `project_xiaoma-data` 仍在） |

即：卸载只清程序本体，不碰用户数据与运行中的服务；要彻底清除见 README 桌面版小节。

### 15.5 边界（如实记录）

- **仍未签名**：`Get-AuthenticodeSignature` 对 `Xiaoma-Setup-1.4.1.exe` 与 `win-unpacked/Xiaoma.exe` 均为 `NotSigned`，本机无代码签名证书；SmartScreen 仍会提示未知发布者。
- **安装包用的是 Electron 默认图标**：打包日志明确输出 `default Electron icon is used reason=application icon is not set`，桌面快捷方式与安装界面因此显示 Electron 图标，属可见缺陷。仓库内没有品牌图标资产，本批**未擅自生成**（不用自己的审美替产品定视觉），建议由产品提供 ≥256×256 的 PNG/ICO 后配置 `build.win.icon` 与 `nsis.installerIcon` 再打包一次。
- **仍是同一台机器**：本次「安装 → 两条启动路径 → 卸载」都在本机完成，只能证明安装包与卸载逻辑可用，不等于全新 Windows（含 Docker Desktop 前置、UAC 提权、首次镜像拉取的网络前提）的完整验证。
