# 小码课程扩展阶段 0：现有项目检查报告

- 检查日期：2026-11-08
- 项目版本：1.0.0（数据库迁移 head：`5a9439936da5`）
- 检查方式：阅读实际代码、Alembic 迁移、运行中的 Docker 容器与 SQLite 数据库；未修改任何业务代码，未执行写库、删除或重建操作。
- 检查范围：项目结构、数据模型、迁移、课程/章节/知识点、学习档案、计划、每日任务、测验、错题复习、Agent、API、Docker 与环境配置。

**结论摘要**

1. 现有数据模型**可以容纳多门课程**，前端课程页也会自动列出全部课程；但用户学习流程仍是**单课程、单计划**，创建计划后无法通过现有前端开始第二门课程。
2. 课程只有 `code/name/description` 三个业务字段，**没有课程方向分类、课程级先修关系、课程版本**；章节与知识点支持，但没有独立的“课时”模型。
3. 知识点级先修、题目关联知识点、用户知识点掌握状态均已实现；现有学习计划、每日任务、测验都引用真实课程数据。
4. Agent 没有直接访问数据库，全部通过 Service 层；但**教学提示词和 AI 出题提示词硬编码了“Python 基础课程”**，扩展新课程必须调整。
5. 课程种子当前只支持**一门课程**，题库校验硬编码 **31 个知识点**；新增课程需要先改造种子与题库校验，否则无法规模化录入。

## 二、现有项目架构

### 2.1 目录结构与分层

```text
backend/app/
  api/v1/         FastAPI 路由（46 个端点）
  services/       业务层（课程、计划、任务、测验、复习、Agent、备份等）
```

### 2.4 API 与前端

- 后端共 46 个路由，覆盖健康检查、登录、备份、课程、知识点、学习档案、计划、每日任务、会话、模型配置、测验、错题、复习、概览。

### 2.5 Agent 架构

```text
用户消息
  → 意图识别（关键词规则，确定性）
  → 读取学习上下文（ProfileService / PlanService）
  → 路由到 planning / teaching / quiz / review / resource 子图
  → AgentToolbox → Service 层
  → SSE 流式回复 → 持久化消息
```

- `agent/tools.py` 只实例化 Service，不导入 Repository、不执行 SQL。
- `agent/context.py` 同样只调用 Service。
- `agent/graph.py` 只编排节点与子图。
- 当前**没有直接数据库访问**，这一点必须保持。

### 2.6 Docker 与环境配置

- `docker-compose.yml`：前后端两个服务；后端不映射宿主机端口，前端默认绑定 `127.0.0.1`；命名卷 `xiaoma-data` 挂载 `/app/data`；健康检查、`depends_on: service_healthy`、`restart: unless-stopped`。
- `backend/entrypoint.sh`：启动时自动执行 `init-db`（Alembic 迁移）、`seed-courses`、`seed-questions`，再启动 uvicorn。
- `.env.example`：访问范围、访问密码、数据库路径、备份目录、Agent 超时、加密密钥等配置。
- 新增课程数据只需重新构建/重启后端（或手动执行种子命令），无需新增服务或基础设施。

## 三、已有课程模块情况

### 3.1 当前课程数据结构

`Course` 只有：

```python
code: str          # 全局唯一，如 python-basics
name: str
description: str | None
```

`Chapter`：

```python
course_id, code (全局唯一), title, description, order_index
```

`KnowledgePoint`：

```python
chapter_id, code (全局唯一), name, learning_goal, difficulty,
estimated_minutes, mastery_criteria, resources(JSON), order_index
```

先修关系只存在于知识点级：

```python
knowledge_point_prerequisites(knowledge_point_id, prerequisite_kp_id)
```

没有 `Lesson`（课时）表，也没有课程级 `course_prerequisites` 表。

### 3.2 课程数据写入方式

- `backend/app/seed/course_seed.py` 中只有一个 `SEED_COURSE` 字典，内容为「Python 通用基础」：6 章、31 个知识点、38 条前置关系。
- `seed_courses()` 按 `code` 幂等 upsert 课程、章节、知识点；前置关系按目标集合与现有集合差集同步；**不删除**种子中已不存在的行。
- `seed-questions` 依赖课程知识点，内置题库当前为 31 个知识点 × 3 题 = 93 题。
- 没有运行时课程管理 API；课程内容变更必须改种子代码并执行命令。

### 3.3 能力判断（重点分析）

| 能力 | 结论 | 代码依据 | 说明 |
| --- | --- | --- | --- |
| 支持多门课程 | **部分支持** | `Course` 表可存多条；`CourseRepository.list_courses()` 返回全部；前端课程页遍历课程 | 数据与展示支持；学习流程只支持一份计划，创建计划后无法通过前端开始第二门课程 |
| 支持课程方向分类 | **不支持** | `Course` 无 direction/category/level 字段；`CourseSummary` 只有 code/name/description/chapter_count | 需要新增字段或分类表；前端目前也不展示分类 |
| 支持章节 | **支持** | `Chapter` 1:N `KnowledgePoint`，按 `order_index` 排序 | 章节 code 全局唯一 |
| 支持课时 | **不支持独立课时模型** | 无 `Lesson`/`CourseLesson` 表 | 当前“知识点”就是最小学习单元（有目标、时长、资源、掌握标准）；若产品中的“课时”等同知识点，可直接复用 |
| 支持知识点 | **支持** | `KnowledgePoint` + 详情 API + 学习任务 + 测验 + Agent | 完整 |
| 支持课程先修依赖 | **课程级不支持；知识点级支持** | `knowledge_point_prerequisites` | 跨课程知识点先修在计划校验中会失败（除非用户自述已掌握），课程级先修完全缺失 |
| 支持课程版本 | **不支持** | `Course/Chapter/KnowledgePoint` 无 version 字段或历史表；种子按 code 原地更新 | 课程内容更新没有版本快照；计划版本只是学习计划版本，不是课程版本 |
| 支持题目关联知识点 | **支持** | `Question.knowledge_point_id` 外键；题库按知识点组卷 | 新课程必须补题目，否则无法测验/掌握 |
| 支持用户知识点掌握状态 | **支持** | `learning_profiles`：user_id + knowledge_point_id 唯一，5 种状态 | 跨课程天然支持，因为状态按知识点记录 |
| 支持课程跳级 | **部分支持** | `PlanCreate.mastered_kp_codes`；前端诊断区可勾选“已掌握知识点” | 只在创建计划时自述跳过；没有后续跳过接口；不校验“已掌握集合”的前置闭包，可能跳过先修知识点 |
| 支持根据学习诊断生成课程路线 | **不支持真正的诊断/路线** | 诊断只是 `PlanCreate` 的输入快照；`plan_scheduler` 按课程顺序装满天数 | 没有诊断题、诊断结果模型、跨课程路线算法；不是 AI 诊断，也不是个性化课程路径 |
| 现有 Agent 是否直接操作数据库 | **否** | `agent/tools.py`、`context.py` 只调用 Service；Agent 目录无 SQL/ORM 查询 | 必须继续保持 |
| 学习计划是否引用真实课程数据 | **是** | `learning_plans.course_id`、`learning_plan_items.knowledge_point_id`、`daily_tasks.knowledge_point_id` | 计划项目、任务、测验都引用真实课程/知识点 |

### 3.4 现有课程模块的具体限制

1. **单课程学习流程**：`PlanService.create_plan()` 在用户已有计划时返回 409；`PlanAdjust` 不包含 `course_code`；`get_current_plan()` 只取最近一份计划。因此同一用户无法并行学习两门课程，也无法在已有一份计划时通过现有 API 切换到另一门课程。
2. **课程级先修缺失**：无法表达“先学 Python 基础，再学 Python 数据分析”这类课程顺序。
3. **跨课程知识点先修不完整**：`validate_schedule()` 的课程知识点集合只包含当前课程；若新课程的知识点前置指向另一门课程的知识点，且用户没有自述已掌握，计划会校验失败。
4. **课程内容无版本**：种子 upsert 会直接更新已有课程/章节/知识点内容；历史计划项目仍指向同一知识点 ID，无法还原旧课程内容。
5. **“诊断”是表单自述**：没有诊断题、诊断结果表或诊断服务；`current_level`、`mastered_kp_codes` 只用于排期。
6. **题库覆盖是硬编码**：`question_seed.py` 要求恰好 31 个知识点、每个 3 题；新增课程知识点后必须改校验逻辑，否则 `seed-questions` 直接报错。
7. **Agent 提示词硬编码 Python**：`teaching_prompt.py` 的角色、边界、无知识点兜底都写死“Python 通用基础课程”；`ai_question_service.py` 的生成/审核提示词也写死“Python 基础课程”。新课程的教学与 AI 出题会出现内容偏差。
8. **前端已有计划后不能选新课程**：计划页在 `hasPlan` 时禁用课程下拉框，且不提供“完成当前课程/创建新计划”的入口。
9. **章节序号显示问题（既有小问题）**：种子 `order_index` 从 1 开始，`LearnClient` 显示 `order_index + 1`，页面会显示“2. 初识 Python”等偏移序号；不属于本次扩展，但建议在后续课程 UI 调整时一并修正。

## 四、可复用的模型和服务

以下现有能力应优先复用，避免为新课程重建一套体系：

| 可复用项 | 位置 | 复用方式 |
| --- | --- | --- |
| 课程/章节/知识点模型 | `backend/app/models/course.py` | 增加课程元数据字段；章节与知识点结构保持不变 |
| 知识点先修关系 | `knowledge_point_prerequisites` | 新课程内部继续使用；是否需要跨课程先修另行决策 |
| 课程查询 Service/Repository | `course_service.py`、`course_repository.py` | 扩展方向筛选、课程级先修、课程字段；不改变现有查询语义 |
| 计划与排期算法 | `plan_service.py`、`plan_scheduler.py` | 保留“课程顺序 + 每日分钟装满 + 前置校验 + 版本化”的确定性算法 |
| 每日任务滚动追赶 | `daily_task_service.py` | 保留“最早未完成计划日整批生成 + 唯一约束防重 + 已掌握排除” |
| 知识点掌握状态 | `learning_profiles`、`learning_profile_repository.py` | 跨课程直接复用；不按课程另建掌握表 |
| 测验与题库 | `quiz_service.py`、`question_repository.py`、`question_seed.py` | 继续按知识点组卷；新课程补题即可；AI 变式题复用现有验证链路 |
| 错题与复习 | `review_service.py`、`mistakes`、`review_tasks` | 无需按课程改造，按知识点自然隔离 |
| Agent 工具与上下文 | `agent/tools.py`、`agent/context.py` | 继续只调用 Service；增加课程名/课程上下文，不直接查库 |
| 种子幂等框架 | `course_seed.py` 的 `_upsert_*` | 改造成多课程列表，保留按 code upsert、不删除用户数据 |
| 备份/访问控制/Docker | `backup_service.py`、`access_*`、`docker-compose.yml` | 完全复用，不因课程扩展改变部署架构 |

## 五、需要新增的模型和服务

以下为**建议**，不是本阶段已实施的改动；具体取舍需产品确认。

### 5.1 建议新增（第一阶段最小集）

| 项 | 类型 | 建议内容 | 目的 |
| --- | --- | --- | --- |
| 课程方向 | `courses` 新字段 | `direction`（String，可空，建索引）；`sort_order`（Integer，默认 0） | 支持课程方向分类与稳定排序；不引入新表，避免过度设计 |
| 课程种子多课程化 | 现有种子改造 | `SEED_COURSES: list[dict]`；全局 code 唯一校验；前置 code 全局解析 | 让一门或多门课程可幂等写入；保持现有 Python 课程不变 |
| 课程 Service 扩展 | `CourseService` | 按方向筛选、输出方向/排序字段、课程级先修（如启用） | 不新增重复服务 |
| 题库种子多课程化 | `question_seed.py` | 期望知识点集合从课程种子推导，不再硬编码 31；每知识点题目数规则明确 | 新课程可以录入题目并通过校验 |
| 动态课程提示词 | `teaching_prompt.py`、`ai_question_service.py` | 从知识点/计划读取课程名，替换硬编码“Python 基础课程” | 教学与 AI 出题适配新课程 |

### 5.2 视产品决策再新增

| 项 | 触发条件 | 说明 |
| --- | --- | --- |
| `course_prerequisites` 表 | 产品要求课程级先修 | 结构类似知识点先修：`course_id + prerequisite_course_id` 联合主键；同时在计划创建/调整时校验用户是否已掌握先修课程 |
| 多计划策略 / 课程切换 Service | 产品要求并行学习多门课程或完成一门后继续下一门 | 需要决定“一名用户同时一份计划还是多份计划”；涉及 `learning_plans` 状态、当前计划指针、每日任务/阶段测验的课程范围 |
| 诊断与课程路线 Service | 产品要求真正的诊断题/跨课程路线 | 新增诊断结果模型与路线算法；不能只靠现有 `mastered_kp_codes` 表单 |
| 课程版本模型 | 产品要求课程内容历史版本 | 需要课程/章节/知识点版本表或内容快照；改造成本较高，建议独立阶段评估 |
| 独立课时模型 | 产品定义“课时”不是现有知识点 | 新增 `lessons` 表、API 与前端层级；本轮“不改前端”约束下不建议 |

### 5.3 不建议新增

- **不新增第二套课程/知识点表**：现有模型已能表达课程→章节→知识点。
- **不新增独立“课程方向”表**：方向值少且稳定时，`direction` 字段足够；若未来方向需要描述、排序、多对多再拆表。
- **不引入新数据库/缓存/任务队列**：课程扩展不构成引入新基础设施的理由。
- **不让 Agent 直接写课程数据**：课程仍由种子/受控 Service 写入，Agent 只读或调用既有 Service。

## 七、需要保留的已有业务逻辑

扩展课程时不得破坏以下规则：

1. **课程种子幂等且不删除用户数据**：按 `code` upsert，前置关系差集同步，不删除种子中不存在的课程/知识点；新增课程不能通过 `delete` + `insert` 实现。
2. **计划版本化**：创建/调整先生成草稿，用户确认后生效；旧版本保留为 `superseded`；已完成项目携带到新版本，不因调整丢失。
3. **每日任务滚动追赶**：取最早未完成计划日的整批未完成、未掌握知识点；同一天同一知识点唯一约束防重复；已掌握知识点不生成任务。
4. **掌握状态只由测验更新**：任务完成只到 `pending_verification`，绝不直接 `mastered`；掌握判定仍需“≥3 题、全部通过、百分制 ≥90”。
5. **测验范围限制**：只能测已学习知识点；章节测验只取该章节已学内容；阶段测验只取当前计划课程已学内容；未学习知识点不得进入正式测验。
6. **题库质量门槛**：正式组卷只读取 `approved` 且 `validation_status in (builtin, ai_validated)` 的题目；AI 变式题必须经过结构校验和独立复核；失败降级为内置题库，不伪造验证成功。
7. **Agent 只调用 Service**：不导入 Repository、不执行 SQL；工具结果区分 `ok/unavailable/failed`，失败不得包装成成功。
8. **软删除与历史保留**：课程/章节/知识点软删除过滤；答题记录、计划历史、聊天历史不因课程扩展被清空。
9. **访问控制、备份恢复、Docker 健康检查**：课程扩展不应改变既有部署与安全边界。
10. **现有测试基线**：V1.0 的 217 项后端测试、14 项前端测试全部通过；课程扩展后必须保持并通过新增测试。

## 八、数据迁移风险

| 风险 | 影响 | 建议缓解 |
| --- | --- | --- |
| SQLite 迁移能力限制 | 当前 `alembic/env.py` 未启用 batch 模式；新增列可行，修改/删除约束会失败 | 第一阶段只新增可空列/新表，不改现有约束；需要改约束时显式使用 `batch_alter_table` 并测试 |
| 课程 code 全局唯一 | 新课程/章节/知识点 code 冲突会导致迁移或种子失败 | 统一课程前缀（如 `python-advanced-`），种子写入前做全局唯一校验 |
| 种子仅支持单课程 | 直接追加课程数据不会被写入；`seed_courses()` 只处理 `SEED_COURSE` | 先改造为 `SEED_COURSES` 列表，再追加新课程 |
| 题库校验硬编码 31 | 新课程题目无法通过 `seed-questions`；执行会直接抛错 | 将期望知识点集合从课程种子推导；明确每个知识点的题目数要求 |
| 测试硬编码单课程 | `test_course_api.py` 断言课程数为 1、章节 6、知识点 31；新增课程后测试失败 | 改为按 code 断言或按数据集断言；新增多课程测试 |
| Docker 启动自动迁移 | 新迁移失败会导致后端无法启动；升级窗口内服务不可用 | 升级前备份数据库；迁移先在测试库跑 upgrade/downgrade/re-upgrade；保留备份恢复路径 |
| 历史计划/任务/答题数据 | 课程内容原地更新会影响历史计划的展示；删除知识点会级联影响计划/答题 | 只做增量 upsert，不删除已有课程/知识点；如需改内容，保留稳定 code 与 ID；重要变更前备份 |
| 课程级先修的跨课程校验 | 现有 `validate_schedule()` 只认识当前课程知识点，跨课程前置会报“未安排在计划中” | 若启用跨课程先修，先扩展校验逻辑与“已掌握”口径，再录入依赖数据 |
| 无课程版本 | 课程内容更新后无法还原旧版本，历史计划可能显示新内容 | 若产品要求可追溯，先设计课程版本模型；否则在发布说明中明确“课程内容原地更新” |
| Agent 提示词硬编码 Python | 新课程教学/AI 出题会围绕 Python 回答，产生错误内容 | 扩展前先改为动态课程名；增加“非 Python 课程”提示词测试 |
| 前端已有计划后无法选新课程 | 数据已录入但用户无法开始新课程 | 这是前端流程限制；本轮“不改前端”只能做到课程目录展示，需在后续阶段补课程切换 UI |
| 既有章节序号偏移 | 课程页显示序号比实际大 1 | 独立小修复，建议在课程 UI 阶段处理，不影响数据模型 |

## 九、课程扩展实施方案（建议）

> 原则：增量扩展、不删除已有数据、不重建项目、不引入新技术栈、暂不改前端。每一步先备份、先测试，再进入下一步。

### 阶段 1：课程元数据与迁移（后端，不改前端）

**目标**：让课程具备方向分类和稳定排序，同时保持现有 Python 课程与学习数据不变。

**任务**

1. 新增迁移：`courses.direction`（可空）、`courses.sort_order`（默认 0，可空/非空按实现决定）；为现有 `python-basics` 回填方向值（方向值待产品确认）。
2. 更新 `Course` 模型、`CourseSummary/CourseDetail` schema、`GET /courses` 输出与可选筛选。
3. 保持 `seed_courses()` 对现有课程的 upsert 行为；新增字段不改变已有课程内容。
4. 增加迁移测试：upgrade → downgrade → re-upgrade；新增列/回填数据正确。
5. 增加 API 测试：旧字段不变，新字段存在；现有课程详情仍返回 6 章 31 知识点。

**验收**：现有 Docker 数据完整；`GET /courses` 仍可用；新字段可见；迁移可回滚；现有 217 项测试通过。

### 阶段 2：多课程种子与首批课程内容（后端 + 内容）

**目标**：支持一门以上课程幂等写入，完成首批新课程内容与题库。

**任务**

1. 将 `SEED_COURSE` 重构为 `SEED_COURSES` 列表；全局解析课程/章节/知识点 code；校验 code 唯一、前置 code 存在、先修不跨课程（或明确跨课程规则）。
2. 按产品提供的课程大纲写入新课程：章节、知识点、目标、难度、预计时长、掌握标准、资源、知识点先修。
3. 改造 `validate_question_definitions()`：期望知识点集合从课程种子推导，不再硬编码 31；明确每知识点题目数量与题型覆盖要求。
4. 为新课程录入内置题库（数量与质量标准由产品确认），同步更新 `BUILTIN_NOTE` 与题库审核文档。
5. 更新测试中硬编码的单课程断言；增加多课程种子幂等、跨课程 code、题库覆盖测试。
6. 执行开发库与 Docker 库的幂等种子；确认原有学习档案、计划、错题、聊天记录不变。

**验收**：`seed-courses` 重复执行不产生重复数据；`GET /courses` 返回多门课程；新课程可在学习页展示；新课程题目可通过校验；旧数据完全保留。

### 阶段 3：多课程学习流程（后端，视前端约束）

**目标**：决定并实现“学完一门课之后如何开始下一门”，以及多课程下计划/任务/测验/概览的归属。

**前置决策**：同一时间只允许一份计划（顺序学习），还是允许多份计划（并行学习）。建议 V1.3 先采用**顺序学习**，降低每日任务与阶段测验的歧义。

**任务（若顺序学习）**

1. 为 `learning_plans` 增加明确的生命周期（如 `completed`/`archived`；当前只有 draft/active），或新增“完成当前计划”Service 方法。
2. 允许用户完成/归档当前计划后创建下一门课程计划；保留旧计划、任务、答题历史。
3. 每日任务、阶段测验、学习概览继续以“当前生效计划”为范围，不混入旧课程。
4. 阶段测验的课程归属保持 `plan.course_id`；章节/知识点测验天然按 code 隔离。
5. Agent 上下文与资源检索使用当前计划课程名；动态提示词改造。
6. 增加 API 测试：旧计划归档后新计划可创建；旧数据可查；每日任务不串课；阶段测验不串课。

**若产品选择并行学习**：需新增“当前学习课程”选择机制、每课程一份计划、任务/测验按课程筛选；改动面更大，应单独立项。

**注意**：本轮“暂不改造前端”意味着阶段 3 只能完成 API/Service 与测试；用户实际切换课程仍需后续前端入口。

### 阶段 4：课程先修、诊断路线与跳级（按产品确认）

**目标**：支持课程级先修、真正的诊断与跨课程学习路线。

**任务**

1. 如启用课程级先修：新增 `course_prerequisites` 表、迁移、Service 校验；在计划创建/调整时检查先修课程是否已完成/已掌握。
2. 如启用跨课程知识点先修：扩展 `validate_schedule()`，允许前置来自其他课程，并定义“已掌握”判定口径。
3. 如启用真正诊断：新增诊断结果模型、诊断题/问卷 API、路线生成 Service；不能把自述表单当作诊断结论。
4. 跳级规则：明确是否允许用户自述跳过、是否要求先修闭包、是否要求测验验证。
5. 增加路线、先修、跳级的自动化测试与数据迁移测试。

**验收**：课程先修可被后端强制执行；诊断结果可追溯；路线不违反先修；历史数据不受影响。

### 阶段 5：前端展示与完整交付（本轮明确不做）

**目标**：让用户看得见、用得上课程方向与课程切换。

**任务**

1. 课程页按方向分组/筛选；修正章节序号显示。
2. 计划页支持完成当前课程后创建下一门课程；多计划时提供切换入口。
3. 测验/概览正确展示课程名，避免跨课程同名章节混淆。
4. 完整回归、Docker 部署验收、备份恢复验收、更新文档与 CHANGELOG。

**验收**：新用户可选择任意课程；老用户可完成一门后开始下一门；所有历史数据可查；Docker 部署通过。

## 十、风险、注意事项与待确认问题

### 10.1 产品范围冲突（必须先确认）

PRD V1.3 的 3.4 节明确将“首版以外的多语言课程体系”列为 V1.0 不包含内容，3.3 节的首发范围也写的是“Python 通用基础课程”。本次“编入新的课程”属于对既有产品范围的扩展，**需要产品负责人明确确认并更新 PRD/任务书**，否则与 CLAUDE.md 中“以产品需求为准、不得擅自增加产品功能”的约束冲突。

### 10.2 需要产品确认的问题

1. **新课程清单**：课程名称、课程方向、章节、知识点、先修关系、预计时长、学习目标、掌握标准、资源、题目数量与来源。
2. **多课程学习模式**：同一时间只学一门（顺序），还是可以并行多门？是否允许同一用户存在多份学习计划？
3. **“课时”定义**：现有“知识点”是否就是产品所说的“课时”？若需要“章 → 课 → 知识点”三级结构，必须新增模型和前端层级。
4. **课程方向枚举**：方向如何命名、如何排序、一门课程是否允许多个方向？
5. **课程版本**：课程内容更新是否需要历史版本/快照？还是允许原地更新并在发布说明中标注？
6. **诊断路线**：是沿用现有“自述 + 排期”，还是要新增诊断题、诊断结果和跨课程路线？
7. **跳级规则**：是否允许用户自述跳过知识点/课程？是否需要前置闭包校验或测验验证？
8. **本轮边界**：是否确认本轮只做课程数据录入与后端准备，前端课程切换/方向展示留到后续？

### 10.3 实施注意事项

- **数据安全**：任何迁移/种子前先备份；不执行 `docker compose down -v`；不删除已有课程、知识点、计划、任务、聊天和答题记录。
- **不伪造内容**：新课程内容必须由产品提供并审核，不得用 AI 自由生成的目录冒充实盘课程；题库沿用现有审核与验证流程。
- **先测后录**：先在测试库验证迁移与种子，再对开发库/Docker 库执行；迁移测试覆盖 downgrade。
- **保持 Agent 边界**：课程扩展不能让 Agent 直接写数据库或直接生成正式课程结构。
- **保持测试基线**：新增课程会改变课程数量与题库覆盖，测试中的硬编码断言必须改为数据驱动或按 code 精确断言。
- **前端约束**：本轮不改前端意味着“课程目录可见”可以先实现，但“已有计划用户开始新课程”必须等前端入口；不要把后端未闭环的能力宣称为已完成。
- **文档同步**：课程扩展涉及产品范围、课程清单、题库审核、部署数据迁移，需同步更新 PRD/任务书、README、CHANGELOG 与开发进度记录。
