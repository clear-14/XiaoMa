# 小码 V1.0 部署操作方案

> 适用版本：1.4.1
> 目标：在一台机器上完成部署、初始化并通过验收，预计 30–60 分钟。
> 本方案是可直接照做的操作清单；原理与更多细节见 [Docker部署指南.md](Docker部署指南.md)。

## 一、选择部署模式

| 模式 | 适用场景 | 访问地址 | 必须配置 | 传输安全 |
| --- | --- | --- | --- | --- |
| A. 本机自用 | 个人电脑，只有自己使用 | `http://localhost:3000` | 无 | 本机回环 |
| B. 局域网共享 | 家庭/公司内网，多台设备 | `http://<宿主机IP>:3000` | 访问密码 | HTTP 明文，仅限可信网络 |
| C. 公网访问 | 互联网访问 | `https://你的域名` | 访问密码 + 反向代理 HTTPS | HTTPS |

首次部署建议先按 A 完成验收，再按需切换到 B 或 C。

## 二、部署前准备

### 2.1 环境检查

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Windows 10/11、Linux、macOS |
| Docker | Docker Engine 24+ 或 Docker Desktop |
| Docker Compose | v2.24+（`docker compose` 命令） |

执行检查：

```bash

docker compose version
docker info
```

Windows 需先启动 Docker Desktop，托盘图标显示运行中；Linux 需确保当前用户可执行 Docker 命令。

## 三、步骤 A：本机部署（基础流程）

### A1. 获取代码

```bash
git clone <仓库地址> XiaoMa
cd XiaoMa
```

已有代码则直接进入目录并确认版本：

```bash
git log -1 --oneline
```

### A2. 创建配置文件

```bash
cp .env.example .env
```

Windows PowerShell：

```powershell
Copy-Item .env.example .env
```

默认内容即为本机模式，无需修改：

```dotenv
BIND_ADDRESS=127.0.0.1
FRONTEND_PORT=3000
```

`.env` 含敏感信息，**不得提交到 Git**。

### A3. 构建并启动

```bash
docker compose up -d --build
```

首次构建需下载基础镜像与依赖，耗时约 5–20 分钟；后续启动为秒级。

### A4. 等待健康检查通过

```bash
docker compose ps
```

预期两个服务均为 `Up (healthy)`：

```text
xiaoma-backend    Up (healthy)   8000/tcp
xiaoma-frontend   Up (healthy)   127.0.0.1:3000->3000/tcp
```

首次启动后端会等待约 30–90 秒（迁移 + 种子数据）。若未通过：

```bash
docker compose logs --tail=100 backend
docker compose logs --tail=100 frontend
```

### A5. 访问并初始化

浏览器打开 <http://localhost:3000>，依次完成：

1. 初始化学习档案（目标、基础水平、每日学习时间等）；
2. 进入「设置」→ 添加模型配置（服务商、模型名、API Key）→「测试连接」成功 → 设为默认模型；
3. 完成诊断；
4. 创建学习计划并确认；
5. 在首页获取今日任务。

## 四、步骤 B：开放局域网访问

> 前提：已按 A 完成部署并验收。局域网内使用 HTTP 明文传输，密码可能被同网段抓包获取，仅建议在可信网络使用。

### B1. 修改 `.env`

```dotenv
BIND_ADDRESS=0.0.0.0
XIAOMA_ALLOW_REMOTE=true
XIAOMA_ACCESS_PASSWORD=请替换为至少16位的强密码
```

三项缺一不可：缺少密码或 `XIAOMA_ALLOW_REMOTE=true` 时，后端会打印错误并**拒绝启动**。

### B2. 重新启动

```bash
docker compose up -d
```

### B3. 放行系统防火墙

- Windows：首次启动时 Docker Desktop 会提示网络访问，选择允许；或在「Windows 安全中心 → 防火墙 → 允许应用」中放行 Docker Desktop。
- Linux（ufw 示例）：`sudo ufw allow 3000/tcp`。

### B4. 获取宿主机 IP 并访问

```bash
# Windows
ipconfig
# Linux / macOS
ip addr
```

其他设备访问 `http://<宿主机局域网IP>:3000`，首次进入需输入访问密码。

### B5. 验证访问保护

```bash
curl -i http://<宿主机IP>:3000/api/v1/profile
# 预期：401 Unauthorized
```

登录后浏览器可正常使用；退出登录或后端重启后需要重新输入密码。

## 五、步骤 C：公网部署（必须 HTTPS）

> 前提：有公网 IP/云服务器与域名；已完成 A 的部署验收。

推荐架构：

```text
公网浏览器 --HTTPS:443--> Nginx/Caddy --HTTP:127.0.0.1:3000--> 小码前端容器
```

### C1. 保持前端仅绑定本机

`.env`：

```dotenv
BIND_ADDRESS=127.0.0.1
FRONTEND_PORT=3000
XIAOMA_ALLOW_REMOTE=true
XIAOMA_ACCESS_PASSWORD=请替换为至少16位的强密码
```

`XIAOMA_ALLOW_REMOTE=true` 时后端启动会强制校验密码非空；前端端口只允许本机反向代理访问。

### C2. 配置域名解析

将 `xiaoma.example.com` 的 A/AAAA 记录指向服务器公网 IP。

### C3. 配置 Nginx 与证书

```nginx
server {
    listen 80;
    server_name xiaoma.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name xiaoma.example.com;

    ssl_certificate     /etc/letsencrypt/live/xiaoma.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/xiaoma.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;        # AI 流式输出（SSE）必须关闭缓冲
        proxy_read_timeout 300s;
    }
}
```

证书可使用 Certbot（`certbot --nginx -d xiaoma.example.com`）或云厂商证书。

### C4. 防火墙只放行 80/443

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

**不要**将 3000 或 8000 端口直接暴露到公网。

### C5. 公网验收

```bash
curl -I https://xiaoma.example.com            # 200，证书有效
curl -i https://xiaoma.example.com/api/v1/profile  # 未登录 401
```

浏览器访问域名 → 输入访问密码 → 完成一次 AI 对话，确认流式输出不卡顿、不整段延迟出现。

## 六、部署后验收清单

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 容器状态 | 两个服务均 `healthy` |
| 2 | 健康接口 | `GET /api/v1/health` 返回 `status: ok`、`version: 1.4.1` |
| 3 | 学习档案 | 可初始化并保存，刷新后仍存在 |
| 4 | 模型 | 「测试连接」成功；API Key 仅显示脱敏值 |
| 5 | 计划 | 诊断后可创建计划并确认 |
| 6 | 每日任务 | 首页可获取今日任务 |
| 7 | 学习与测验 | 可完成知识点学习、提交测验并看到评分 |
| 8 | 错题与复习 | 答错后错题本有记录，生成复习任务 |
| 9 | 聊天历史 | 对话流式输出正常，刷新后历史仍在 |
| 10 | 备份 | 设置页可创建备份并在列表看到 |
| 11 | 访问控制（B/C） | 未登录 API 返回 401，登录后可正常使用 |
| 12 | 日志脱敏 | `docker compose logs backend` 无完整 API Key / 密码 |

参考命令：

```bash
curl http://localhost:3000/api/v1/health
docker compose logs backend | grep -iE "sk-[A-Za-z0-9]{16,}" || echo "未发现完整密钥"
```

## 七、备份策略

### 7.1 日常备份

方式一（推荐）：设置页 → 数据备份 → 立即备份，并下载到宿主机保存。

方式二：命令行：

```bash
docker compose exec backend python -m app.cli backup-db
docker compose exec backend python -m app.cli list-backups
docker compose cp backend:/app/data/backups/<文件名>.db ./xiaoma-backup-$(date +%F).db
```

### 7.2 定时备份（Linux 示例）

宿主机 crontab（每天 03:00，备份后复制到宿主机目录）：

```cron
0 3 * * * cd /opt/XiaoMa && docker compose exec -T backend python -m app.cli backup-db >> /var/log/xiaoma-backup.log 2>&1
5 3 * * * docker compose -f /opt/XiaoMa/docker-compose.yml cp backend:/app/data/backups /opt/xiaoma-offsite/ >> /var/log/xiaoma-backup.log 2>&1
```

建议保留策略：最近 7 天每日 1 份 + 每月 1 份，并至少一份异机/离线保存。

### 7.3 完整迁移必须包含密钥

数据卷 `/app/data` 中有两项关键内容：

| 文件 | 作用 | 缺失后果 |
| --- | --- | --- |
| `xiaoma.db` | 全部业务数据 | 学习数据丢失 |
| `.secret_key` | 解密模型 API Key | 已保存的模型密钥无法解密，需重新填写 |

Web 备份只备份数据库，**不包含 `.secret_key`**。整机迁移时额外导出：

```bash
docker compose cp backend:/app/data/.secret_key ./xiaoma-secret_key.bak
```

`.secret_key` 属于秘密文件，需与备份分开加密保管。

## 八、恢复数据

```bash
# 1. 查看可用备份（也可先在设置页查看）
docker compose exec -T backend python -m app.cli list-backups

# 2. 停止后端（前端可保持运行，但恢复期间页面无法取数）
docker compose stop backend

# 3. 恢复（自动先备份当前数据库为 pre-restore-*.db）
docker compose run --rm --no-deps backend python -m app.cli restore-db <备份文件名> --yes

# 4. 启动
docker compose start backend
```

恢复后刷新页面并核对学习档案、计划、聊天记录。若结果异常，可用自动生成的 `pre-restore-*.db` 再次恢复回退。

**新机器灾难恢复**：先按 A1–A3 启动一次（创建数据卷），然后：

```bash
docker compose cp ./xiaoma-backup.db backend:/app/data/backups/
docker compose cp ./xiaoma-secret_key.bak backend:/app/data/.secret_key
docker compose stop backend
docker compose run --rm --no-deps backend python -m app.cli restore-db xiaoma-backup.db --yes
docker compose start backend
```

## 九、升级与回滚

### 9.1 升级

```bash
# 1. 先备份
docker compose exec backend python -m app.cli backup-db

# 2. 拉取新代码并重建
git pull
docker compose up -d --build

# 3. 观察启动与迁移
docker compose logs -f backend
docker compose ps
```

后端启动脚本会自动执行 Alembic 迁移与幂等种子；数据卷保持不变。

### 9.2 回滚

```bash
git checkout <升级前的提交或标签>
docker compose up -d --build
```

若新版本已执行不兼容的数据库迁移，回滚代码后可能无法读取数据，此时使用升级前备份恢复（见第八节）。

## 十、日常运维

```bash
docker compose ps                  # 状态
docker compose logs -f backend     # 后端日志（Ctrl+C 退出）
docker compose restart             # 重启
docker compose down                # 停止并删除容器（保留数据卷）
docker compose up -d               # 启动
```

**禁止**执行 `docker compose down -v`，`-v` 会删除数据卷，导致全部学习数据与密钥丢失。

建议每月检查：磁盘空间（`docker system df`、`df -h`）、备份可用性（定期试恢复）、镜像更新（`docker compose build`）。

## 十一、安全核对表

部署完成后逐项确认：

- [ ] 本机模式：`BIND_ADDRESS=127.0.0.1`，局域网无法访问 3000 端口；
- [ ] 局域网/公网模式：已设置强访问密码，且 `XIAOMA_ALLOW_REMOTE=true`；
- [ ] 后端 8000 端口未映射到宿主机；
- [ ] 公网只开放 80/443，HTTPS 证书有效；
- [ ] `.env` 与 `.secret_key` 未提交 Git、未随代码分发；
- [ ] 日志中无完整 API Key、访问密码；
- [ ] 备份文件存放在受控位置，迁移时同时保管 `.secret_key`。

## 十二、故障速查

| 现象 | 处理 |
| --- | --- |
| 容器一直 `starting` / 不健康 | `docker compose logs backend` 查看迁移或数据卷错误；首次启动等待 90 秒 |
| 端口被占用 | 修改 `.env` 的 `FRONTEND_PORT` 后 `docker compose up -d` |
| 局域网打不开 | 检查 `BIND_ADDRESS=0.0.0.0`、防火墙放行、使用正确 IP |
| 修改密码后旧会话仍可用 | 重新 `docker compose up -d` 使后端重启，旧令牌全部失效 |
| 页面提示无法连接服务器 | 确认两个容器 healthy；查看 frontend 日志中的代理错误 |
| 模型测试连接失败 | 检查服务商地址、模型名、Key、服务器出网情况 |
| 恢复后模型 Key 失效 | 恢复时未带上匹配的 `.secret_key`，在设置页重新填写 Key |
| AI 回复不是流式 | 反向代理未关闭 `proxy_buffering`，按 C3 修改 |
