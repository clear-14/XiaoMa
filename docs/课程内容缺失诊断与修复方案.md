## 二、根因

`backend/entrypoint.sh` 里容器启动时只执行了 **3 个**种子命令：

```sh
python -m app.cli init-db          # 迁移
python -m app.cli seed-courses     # 旧版课程目录 + python-basics 旧版 6 章
python -m app.cli seed-questions   # 题库
```

而完整内容需要 **8 个**。缺的这 5 个正是"内容"本身：

| 缺失命令 | 负责内容 | 影响的课程 |
|---|---|---|
| `seed-textbook` | 20 章 29 课时教材 + 60 知识点 + 正文 + 练习 | python-basics |
| `seed-phase4a` | 两门课教材 | python-advanced、python-database |
| `seed-phase4b` | FastAPI 教材 | fastapi-backend |
| `seed-phase4c` | 大模型 API 教材 | llm-api |
| `seed-phase4d` | LangGraph 教材 | langgraph-agent |

**为什么本机开发时是好的**：开发期手动跑过全部种子，所以 `backend/data/xiaoma.db` 是完整的。
**为什么重建镜像没用**：`docker compose up --build` 只会重新构建镜像并重跑 `entrypoint.sh`，而 `entrypoint.sh` 里本来就没有这 5 条命令。重建一百次结果都一样。
**为什么数据卷里是旧的**：`xiaoma-data` 是命名卷，容器重建不会清空，早期那 3 条种子的结果一直留在里面。

一句话：**启动脚本漏配，导致容器永远只装了"目录"，没装"内容"**。

## 三、修复方案

### 方案 A：容器内补跑缺失的 5 个种子（推荐）

不动数据卷结构，不丢已有学习记录，幂等命令可重复执行。

```bash
cd /d/XiaoMa
docker compose exec backend python -m app.cli seed-textbook
docker compose exec backend python -m app.cli seed-phase4a
docker compose exec backend python -m app.cli seed-phase4b
docker compose exec backend python -m app.cli seed-phase4c
docker compose exec backend python -m app.cli seed-phase4d
```

| 优点 | 缺点 |
|---|---|
| 保留容器内已有的 1 个学习计划、93 个计划项、12 条每日任务 | 需要先备份（见风险） |
| 命令幂等，失败可重跑 | 首次耗时约 1–3 分钟 |
| 不需要停服务 | — |

### 方案 B：用本地完整库覆盖数据卷

```bash
docker compose stop backend
docker compose cp backend/data/xiaoma.db backend:/app/data/xiaoma.db
docker compose start backend
```

| 优点 | 缺点 |
|---|---|
| 一步到位，本地库已验证完整 | **会丢掉容器内 12 条已完成任务 + 1 个计划**（真实学习进度） |
| | 本地库的 `.secret_key` 与容器不同，模型 Key 可能无法解密，需重填 |

**不推荐**。用户的真实进度比省一步操作重要，而且模型配置会掉。

### 方案 C：修 `entrypoint.sh`（必须做的配套，不能省）

即使这次用命令行补完了，**下次换台机器装、或清空数据卷重来，问题会原样复现**。必须把 5 条命令写进启动脚本，让"首次启动即可用"这件事真正成立：

```sh
echo "正在写入课程种子数据（幂等）..."
python -m app.cli seed-courses

echo "正在写入零基础入门教材（幂等）..."
python -m app.cli seed-textbook

echo "正在写入进阶与数据库教材（幂等）..."
python -m app.cli seed-phase4a

echo "正在写入 FastAPI 教材（幂等）..."
python -m app.cli seed-phase4b

echo "正在写入大模型 API 教材（幂等）..."
python -m app.cli seed-phase4c

echo "正在写入 LangGraph 教材（幂等）..."
python -m app.cli seed-phase4d

echo "正在写入内置题库（幂等）..."
python -m app.cli seed-questions
```

代价：容器首次启动时间会从约 30 秒增加到约 90–120 秒。可接受，因为只在空卷时才有实际写入。

### 推荐执行顺序

```
备份 → 方案 A 补内容 → 接口校验 → 方案 C 改脚本 → 重建验证
```

## 四、风险点（必须先看）

### 风险 1：课时级联删除可能带走已完成的每日任务

`daily_tasks.lesson_id` 外键是 `ondelete="CASCADE"`。而 `textbook_writer.py` 有一段清理逻辑：

```python
# 清理不在新目录中的旧课时（仅在无正文时）
if lesson.content is not None:
    stats["knowledges_kept"] += 1   # 有正文的保留
    continue
db.delete(lesson)                    # 无正文的直接物理删除
```

容器里的 python-basics 是旧版 6 章 14 课时，且**所有课时都没有正文**（`course_contents = 0`），所以全部满足"可删除"条件。新版教材的课时 code 若有变化，旧课时会被删 → 引用它的 `daily_tasks` 可能级联消失。

**处置**：执行前必须在容器内备份，执行后比对任务数。

```bash
docker compose exec backend python -m app.cli backup-db
```

备份落在数据卷 `/app/data/backups/`，可下载留档。

### 风险 2：知识点复用依赖 code 一致

旧任务引用的是 `python-basics-01-01` 这类 code。教材种子按 code 复用知识点（`knowledge_points_reused`），只要 code 不变，任务不会悬空。若个别 code 变了，对应任务会失效但不报错。

**处置**：补完后逐条核对 12 条任务的 `knowledge_point_id` 是否仍能 join 到知识点。

### 风险 3：模型 Key 解密

方案 A 不动 `.secret_key`，模型配置完好。方案 B 会破坏，这也是不推荐 B 的原因之一。

### 7.4 修复过程中的 3 个真实缺陷

| # | 问题 | 现象 | 修复 |
|---|---|---|---|
| 1 | 判断题答案格式不符判分契约 | `true_false` 的 `correct_answer` 写成 `{"value": "A"}` 且带 A/B 选项，判分时抛 `判断题正确答案配置无效` | 改为 `{"value": true/false}`，`options` 置空（28 题） |

| 3 | 教材验收的「示例代码」判定只认 Python | 部署类课程的可运行片段是 `git`/`docker`/`nginx`/compose 配置，被判定为「不像可运行片段」 | `textbook_service.CODE_SAMPLE_TOKENS` 增补命令行与配置文件线索（`$ `、`git `、`docker`、`curl `、`nginx`、`services:`、`FROM `/`RUN `/`CMD `、`#!/`），判定语义不变、不再误伤运维类课程 |
